# Архитектура APDU Band Bridge

Проект проверяет, способен ли браслет передать APDU своего NFC-контроллера на Pixel по BLE и вернуть ответ считывателю. Один синтетический аппаратный прогон на `miwear.watch.p67glt` / `3.201.026` завершился успешно. Платёжный обработчик в этой цепочке отсутствует.

## Путь данных

```text
Pixel: NFC ReaderMode / IsoDep
          │ SELECT тестового AID, затем случайный challenge
          ▼
Браслет: NFC-контроллер → маршрут AID к основному процессору
          │ NCI DATA → нативный модуль → BLE notify
          ▼
Pixel: независимый BLE-обработчик APDU
          │ вычисление тестового ответа → BLE write с подтверждением
          ▼
Браслет: нативный модуль → штатный NFC send → ответ по RF
          │
          ▼
Pixel: IsoDep получает ответ и сверяет его с журналом BLE
```

В этом опыте Pixel выполняет две роли: внешний NFC-считыватель и удалённый обработчик APDU. Обработчик BLE не получает challenge напрямую из кода считывателя: запрос должен фактически пройти через NFC браслета. Результат `PASS` требует совпавшего BLE-запроса, подтверждённой последней ATT-записи ответа и правильного ответа по NFC. Это проверяет транспортный цикл, но не работу с банковским терминалом.

Тестовый AID — `F04D424150445501`. На `00A4040008F04D42415044550100` обработчик отвечает `9000`. На `8010000010<16 случайных байт>00` он возвращает 16 байт в обратном порядке с XOR `A5`, затем `9000`. В [сохранённом прогоне](evidence/pixel-gatt-v6-observation.json) весь тест занял 396,5 мс; отдельные задержки звеньев пока не измерены.

## Запуск и очистка NFC

1. До старта сверяются модель, версия прошивки и контрольные байты внутренних функций. Это привязка к одному бинарному образу, а не стабильный SDK производителя.
2. `QUERY` должен подтвердить `STOPPED`; `INFO` читает сохранённые штатным стеком возможности контроллера.
3. `START_NFC` останавливает discovery, получает текущую таблицу маршрутов и добавляет только точный тестовый AID. В v6 запись ставится перед остальными; байты и взаимный порядок исходных TLV сохраняются. После SET выполняется GET-проверка, затем разрешается тестовый RF-сеанс.
4. После `READY` Pixel включает NFC-считыватель. Модуль принимает только собственную тестовую сессию; штатная цепочка обработки остальных сообщений сохраняется.
5. `STOP_NFC` читает актуальную таблицу, удаляет свой маршрут, проверяет результат и восстанавливает discovery и callback. Подтверждение ATT-записи команды само по себе не означает завершение очистки: нужны `STOPPED` и последующий `QUERY → STOPPED`.

При частичной записи таблицы восстановление исходного снимка допустимо лишь при однозначном состоянии. Если обнаружены несовместимые внешние изменения, модуль остаётся в `RECOVERY`. Глобальная блокировка обновлений маршрутизации штатного стека не установлена. Во время опыта не следует одновременно менять NFC-настройки или карты.

Модуль должен оставаться в памяти до перезагрузки: асинхронные callback могут ещё ссылаться на его код. `rmmod` не используется. Установка следующей версии начинается с обычной перезагрузки браслета; после неё загрузка вручную через INSTALL требуется снова.

## Ограничения текущего прототипа

- Сеанс ограничен 120 секундами, ожидание APDU — 3 секундами. ISO-DEP WTX не реализован.
- CAPDU ≤261 байта, RAPDU ≤258 байт; первый SELECT должен помещаться в один NCI DATA-пакет.
- Android-приложение работает на переднем плане. Работа после сна циферблата, в фоне, при обрыве и длительном простое требует повторных аппаратных тестов.
- Проверен один успешный цикл. Нет серии измерений, испытаний банковским терминалом или проверки одновременных изменений штатной NFC-маршрутизации.
- ELF занимает 31 112 из 31 272 байт слота шаблона. Расширение функциональности требует контроля размера или отдельного исследования контейнера FACE.

## Граница интеграции Mir Pay

Сейчас BLE-запросы заканчиваются в синтетическом обработчике Android. Обычное приложение не может просто передать их в HCE-сервис установленного Mir Pay: на проверенном штатном Pixel `bindService` отклонён из-за `BIND_NFC_SERVICE` уровня `signature`. Найденные app2app и wearable-интерфейсы не предоставили подтверждённого внешнего входа APDU.

Это отдельная зависимость дальнейшего проекта: нужен поддерживаемый API или согласованная интеграция кошелька на SDK. Наличие транспорта NFC/BLE эту зависимость не снимает. Подробные доказательства находятся в [`evidence/mirpay/`](evidence/mirpay/), следующие этапы — в [roadmap](roadmap.md).
