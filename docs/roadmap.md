# Roadmap

Состояние на **13 ноября 2026 года**. Ближайшая цель — превратить один успешный синтетический прогон в воспроизводимый стенд. Оплата браслетом — отдельная цель с внешней зависимостью: нужен поддерживаемый платёжный интерфейс.

- [x] Реализована загрузка собственного ARM-модуля через Lua-циферблат; корректный запуск подтверждён на браслете.
- [x] Поднят собственный GATT-сервис, подтверждён обмен `QUERY → STOPPED` с совпавшим sequence и завершённой ATT-записью.

- [x] Реализованы сохранение таблицы маршрутов, временное добавление тестового AID, проверка GET после SET и восстановление при STOP.
- [x] Исправлен порядок маршрутов: тестовый AID помещён первым, прежние записи и их взаимный порядок сохранены.

## 1. Воспроизводимость и наблюдаемость

- [ ] Сохранять итог PASS/FAIL отдельно от текущего состояния соединения. Автоматический QUERY после STOP сейчас может заменить видимый результат текстом о готовности BLE.
- [ ] Добавить экспорт журнала и короткого отчёта: версии APK/модуля/прошивки, sequence, длительность, результат проверки ответа и подтверждение очистки.
- [ ] Провести минимум 100 последовательных синтетических прогонов; сохранить долю успеха, p50/p95/max задержки и причины отказов.
- [ ] Проверить повторный запуск после STOP, перезапуска приложения и перезагрузки браслета.

**Критерий готовности:** серия воспроизводится на той же сборке; каждый PASS имеет свежий запрос, BLE-доказательство, завершённую запись ответа и подтверждённый STOP. Ошибки сохраняются и не превращаются в успешный результат.

## 2. Ручные сеансы и восстановление

Принят ручной режим с активным экраном: пользователь будит браслет перед использованием. Постоянная работа во сне и принудительное удержание бодрствования исключены из ближайшего плана. Пробуждение по событию поля NFC описано только в [ТЗ](technical-spec.md); реализация отложена по запросу пользователя.

- [ ] Установить причину отсутствия STATUS при повторном STOP после длительного простоя. На v5 такой эпизод наблюдался после ранее подтверждённой очистки; связь с выключением экрана/таймерами пока не доказана.
- [ ] Проверить повторные ручные сеансы, завершение при уходе с циферблата/приложения, разрыв связи и повторное подключение.
- [ ] На стенде воспроизвести потерю BLE во время APDU и на этапах изменения/восстановления маршрутов.
- [ ] Уточнить защиту от одновременного изменения таблицы штатным стеком. GET-уведомления не содержат идентификатора транзакции, общей блокировки сейчас нет.

**Критерий готовности:** каждый сценарий либо заканчивается проверенной очисткой, либо явно оставляет диагностируемое состояние RECOVERY. Ни одна неоднозначная ситуация не выдаёт ложный STOPPED. Старые ответы не принимаются после нового подключения.

## 3. Совместимость NFC и временные ограничения

- [ ] Повторить синтетические тесты с независимым NFC-считывателем, а не только с тем же Pixel, который обрабатывает BLE.
- [ ] Измерять отдельно SELECT, challenge, Bluetooth-доставку, ATT callback и восстановление. Текущие 396,5 мс характеризуют весь прогон.
- [ ] Проверить допустимые размеры CAPDU/RAPDU и фрагментацию на оборудовании, включая границы 261/258 байт.
- [ ] Исследовать ISO-DEP WTX и лимиты времени считывателей, если измерения покажут необходимость. Реализация WTX пока отсутствует.
- [ ] Проверить необходимость поддержки фрагментированного первого SELECT; сейчас он должен помещаться в один NCI-пакет.

**Критерий готовности:** журнал независимого считывателя подтверждает те же данные, что BLE-журнал; длительности и ограничения описаны для каждого проверенного устройства. Это ещё не испытание платёжного протокола.

## 4. Надёжность сборки и переносимость

- [ ] Освободить место или подготовить проверенное расширение формата пакета: у ELF v6 осталось **160 байт** в текущем слоте. Не удалять проверки восстановления ради размера.
- [x] Автоматизирована проверка проекта: 32 fingerprints по сохранённому образу прошивки, хеши четырёх релизов, точная повторная упаковка FACE и доказательство challenge из аппаратного журнала. Модель и версия проверяются при загрузке модуля.
- [x] Сохранены последние проверенные APK 0.4, модуль/FACE v6 и диагностический APK 0.1 с manifest и SHA-256; новые сборки вынесены отдельно. На текущем окружении ELF/FACE воспроизводятся побайтно, а повторные сборки APK имеют одинаковые хеши. Содержимое APK сверено с сохранёнными релизами; побайтовая воспроизводимость между версиями инструментов не проверена.
- [ ] Для следующего выпуска закрепить процесс: обновление версии и manifest, новый аппаратный отчёт, хеши точных проверенных артефактов. Успешная локальная сборка не заменяет испытание на устройстве.
- [ ] Для новых прошивок заново восстановить ABI/адреса и пройти весь набор проверок. Автоматическое снятие version/fingerprint gate не является переносом.
- [ ] Установить лицензию собственного кода и условия использования сторонних шаблона/образа перед публикацией проекта.

**Критерий готовности:** сборка из документированного окружения проходит проверки ELF, упаковки и тесты; артефакты однозначно связаны с исходниками и аппаратным отчётом. Неподдерживаемая прошивка отклоняется до вызова внутренних функций.

## 5. Модель доступа к мосту

- [ ] Документировать, кто может подключаться к экспериментальному GATT-сервису и запускать NFC-сеанс.
- [ ] Проверить поведение сопряжения и шифрования BLE на точной прошивке; определить требования к аутентификации телефона.
- [ ] Проверить посторонний central, повтор сообщений, смену соединения и повторное использование старого sequence на оборудовании.
- [ ] Определить требования к управлению сеансом и хранению данных до расширения синтетического whitelist.

**Критерий готовности:** есть проверенная модель доверия, а отклонение неподходящего клиента и устаревших сообщений подтверждено тестами. Текущий PASS доказывает программный путь данных, а не аппаратно заверенную идентичность участников.

## 6. Платёжная интеграция — внешняя зависимость

**Текущий блокер:** установленный Mir Pay не предоставляет найденному обычному APK доступ к своему HCE-обработчику. Android отклоняет bind из-за `BIND_NFC_SERVICE`; вкладка «Устройства» и app2app SDK не являются APDU-релеем.

- [ ] Получить документированный интерфейс Mir Pay для внешнего APDU-транспорта либо доступ к отдельному Mir HCE SDK и его интеграционной документации.
- [ ] Подтвердить, допускает ли выбранный интерфейс внешнее NFC-устройство через BLE, как выполняются регистрация приложения/устройства и выпуск токенов.
- [ ] Выбрать архитектуру по документации: обработка на Android или поддерживаемый кошелёк на браслете. Наличие HarmonyOS-приложения не подтверждает возможность его переноса на Vela.
- [ ] Сначала проверить разрешённый интеграционный вход и сценарий на тестовой среде/тестовых реквизитах, предусмотренных поставщиком SDK.
- [ ] После появления работающего платёжного обработчика проверить полный протокол, временные ограничения, жизненный цикл токена, поведение блокировки и восстановление. Реальный платёж — отдельный завершающий этап.

**Критерий готовности первого шага:** существует конкретный поддерживаемый контракт, доступный SDK/API и подтверждённая возможность подать в него внешний APDU. Пока этого нет, расширение BLE-протокола, смена AID или успешный DEVICE_BINDED не решают блокер.

Mir HCE SDK и Mir Pay SDK app2app — разные продукты. Публичное описание Mir HCE SDK не даёт доступа к токенам установленного Mir Pay и не подтверждает работу Vela/BLE.
