# Автономные приложения на браслете: что можно сделать без постоянного участия телефона

Состояние на **17 ноября 2026 года**. Устройство: **Mi Smart Band 10 Pro Ceramic Global**,
`miwear.watch.p67glt`, прошивка **3.201.026**. Документ опирается на уже проверенные
результаты проекта и явно отделяет реализованное от предполагаемого.

> **Статус пункта 1 на 17 ноября 2026:** локальный NDEF Type 4 реализован как
> кандидат в ветке `feat/local-ndef-responder` (issue #9). Собран
> `build/roundabout-ru-nfc-local.face`, host-тесты проходят. Аппаратная проверка
> ещё не выполнена; чеклист — [local-ndef-acceptance.md](local-ndef-acceptance.md).

## 1. Короткий вывод

Платформа уже позволяет запускать на браслете собственный native-код, хранить данные в
`/data`, рисовать экран, управлять NFC-маршрутизацией и принимать APDU. Но в проверенной
сборке **APDU обрабатывает Pixel**: браслет — транспорт, а не самостоятельный обработчик.
Поэтому «синхронизировал один раз и всё» сегодня работает для **данных**, но не для
**NFC-обмена**.

Ключевой следующий шаг — **локальный ответчик на браслете**. Для NDEF Type 4 это небольшая
инженерная работа: протокол состоит из SELECT и READ BINARY, данные уже лежат в каталоге,
ответ отправляется через `nfc_probe_send` без Bluetooth. После этого телефон нужен только
для синхронизации, а не для использования.

Что реально даёт автономность в ближайшие недели:

1. **Автономные NDEF-метки** — визитка, Wi-Fi, медкарта, ссылка на оплату, произвольный NDEF.
2. **Экранные QR/штрихкоды** — лояльность, статические билеты, приём оплаты по СБП.
3. **TOTP-аутентификатор** — с оговорками по хранению секретов.

Что пока не даёт:

- **Mir Pay и банковские карты** — внешний блокер: HCE-служба Mir Pay недоступна обычному
  приложению, нужны токенизация, ключи и сертификация.
- **Транспортные карты, защищённые пропуска, ключи автомобиля** — нужен эмитент и
  защищённый элемент, а не только наш код.
- **«Просто поднести, не открывая приложение»** — пробуждение по RF-полю не реализовано и
  не проверено; расход батареи не измерен.

## 2. Что уже есть у платформы

Штатная прошивка уже закрывает тренировки, сон, пульс, погоду, будильники и другие
повседневные функции без телефона. Речь ниже — о **сторонних приложениях**, которых в
прошивке нет: пропусках, метках, документах, платёжных ссылках и подобных сценариях.

| Возможность | Статус | Значение для автономных приложений |
| --- | --- | --- |
| Свой ARM-модуль | Загружается из Lua-циферблата через `insmod`, остаётся в памяти до перезагрузки | Можно сделать отдельное приложение, а не только циферблат |
| Автозагрузка | Lua-таймер после перезагрузки поднимает модуль; часть проверок в документации ещё требует аппаратного подтверждения | После перезагрузки приложение доступно без телефона, но зависит от установленного циферблата |
| Хранение | `/data/tag_catalog`: 32 записи, NDEF до 1024 байт, SHA-256, staging + `rename` | Данные переживают перезагрузку; чтение и выбор не требуют BLE |
| Native UI | Экран 336×480, карточка, кнопки, статусы, меню приложений | Можно сделать полноценный экран приложения |
| NFC-маршрутизация | Временный AID-маршрут, приём CAPDU, отправка RAPDU; один аппаратный PASS за 396,5 мс | Браслет уже умеет говорить с считывателем; не хватает локального ответа |
| BLE | Собственный GATT-сервис, синхронизация каталога | Телефон нужен для настройки и обновления данных |
| eSE | Маршрутизация card emulation к eSE найдена статически | Потенциально пропуска и транспорт, но только через эмитента |
| RF-пробуждение | Не реализовано; статически найдены callbacks | «Поднести и сразу считать» пока нет |
| Питание и сон | Работа после сна не проверена, расход не измерен | Нельзя обещать фоновый режим |
| Оплата | Mir Pay не подключён | Платёжным приложением это не станет без внешней интеграции |

## 3. Три уровня автономности

| Уровень | Что работает без телефона | Что для этого нужно | Статус |
| --- | --- | --- | --- |
| **0. Данные** | Просмотр каталога, выбор записи, экранные карточки | Уже есть | Работает |
| **1. Локальный NFC-ответчик** | Браслет сам отвечает считывателю содержимым NDEF | Перенести обработчик APDU с Pixel на браслет | Инженерная задача, внешних зависимостей нет |
| **2. «Поднести и всё»** | Сеанс стартует от поля, без открытия приложения | RF-wake, фоновая готовность, энергобаланс | Исследование, не реализовано |
| **3. Защищённые пропуска и оплата** | Турникет, транспорт, банковский терминал | Ключи, eSE, эмитент, сертификация | Внешняя зависимость |

Важно: уровень 1 уже снимает главное ограничение «нужен подключённый Pixel». Уровень 2
нужен для удобства, но не обязателен для первого продукта.

## 4. Портфель приложений

Сроки ниже — грубые оценки для одного разработчика, уже знакомого с этой кодовой базой.
Это не обещание сроков: аппаратная приёмка и проверка считывателей могут занять больше.

### 4.1. Ближайшие, без внешних зависимостей

| Приложение | Что синхронизируется один раз | Что происходит без телефона | База и объём работ | Главные риски |
| --- | --- | --- | --- | --- |
| **Автономный NDEF-кошелёк** | До 32 NDEF-записей: ссылка, текст, vCard, Wi-Fi, geo, tel | Браслет отдаёт выбранную запись NFC-считывателю, который понимает NDEF Type 4 (чаще всего — телефону) | Локальный Type 4 NDEF-ответчик; порт `Type4Ndef` на C; 1–2 недели | Читают телефоны и NDEF-ридеры, а не турникеты; данные публичны |
| **Медкарта / ICE** | Группа крови, аллергии, лекарства, контакты | Экран + NDEF для первого спасателя или прохожего | Шаблон NDEF + экран; 3–5 дней после кошелька | Данные видны любому; нет звонка; нужен минимум сведений и согласие |
| **Цифровая визитка** | vCard или URL на профиль | Получатель прикладывает телефон и сохраняет контакт | Шаблон NDEF; 1–2 дня | Ценность только при живом нетворкинге; URL должен быть доступен |
| **Гостевая Wi-Fi** | NDEF Wi-Fi-конфигурация | Гость прикладывает телефон и подключается к сети | Шаблон NDEF; 1–2 дня | Пароль публичен; только гостевая сеть; iOS поддерживает не все сценарии |
| **Приём оплаты по QR СБП** | Статический QR или ссылка на оплату | Покупатель сканирует экран и платит со своего телефона | Рендер QR/предрендер на телефоне; 1–2 недели | Это не Mir Pay; нет подтверждения оплаты; лимиты и правила банка; яркость и размер экрана |
| **Кошелёк лояльности и билетов** | Штрихкоды/QR: карты лояльности, статические билеты, пропуска | Кассир или сканер считывает с экрана | Рендер Code128/EAN13/QR или готовая bitmap; 2–4 недели | Размер и яркость экрана; не все сканеры; ротирующиеся коды не работают |
| **TOTP-аутентификатор** | Семена TOTP | Браслет показывает 6-значный код и таймер | Реальное время, хранение секретов, PIN; 2–4 недели | Нет подтверждённого доступа к secure element; секреты надо шифровать; дрейф часов; фишинг |

**Почему NDEF-кошелёк — первый.** Он переиспользует почти всё, что уже есть: каталог,
хранилище, экран, маршрутизацию, проверку модели/прошивки. Меняется только место обработки
APDU. Это единственный сценарий, где после синхронизации телефон действительно не нужен,
и его можно проверить независимым считывателем.

**Почему QR-кошелёк — второй.** Он не трогает NFC-стек и даёт широкую бытовую пользу:
лояльность, билеты, пропуска, приём чаевых. Но экран браслета маленький и изогнутый:
совместимость со сканерами нужно проверять на реальных устройствах, а не на рендерах.

**Почему TOTP — третий.** Полезно, но требует реального времени и защищённого хранения.
Сейчас `native_clock_ms` привязан к `CLOCK_MONOTONIC`; для TOTP нужен `CLOCK_REALTIME` или
калибровка. Без PIN и шифрования хранить семена нельзя.

### 4.2. Исследовательские направления

| Направление | Идея | Что уже известно | Что нужно проверить | Оценка |
| --- | --- | --- | --- | --- |
| **Домофон по UID** | Браслет отдаёт UID существующего MIFARE Classic-пропуска | Найдены `CORE_SET_CONFIG`, `NFC_SetConfig`, шаблон `LA_NFCID1`; `nfc_nfcid_set_config_callback` — заглушка | Принимает ли контроллер новый UID; видит ли домофон; сохраняется ли профиль; восстановление после опыта | 2–6 недель, высокий риск |
| **Статический APDU-пропуск** | Браслет отвечает заранее записанными ответами простого ISO14443-4 приложения | Локальный APDU-ответчик уже нужен для NDEF; eSE-маршрут существует | Есть ли у реальной системы статический обмен без крипты; законность клонирования | Только свои системы, не продукт |
| **eSE-пропуск / транспорт** | Виртуальный пропуск или транспортная карта в eSE | `SeApi_open_card_emulation_lower_layer` и маршрут к eSE найдены статически; выпуск не подтверждён | Доступ к eSE, апплет, персонализация, сертификация эмитента | Месяцы, только с партнёром |
| **RF-wake / always-on** | Поднести браслет — сеанс стартует сам | Найдены `rfFieldStatusCb` и `nfc_rf_resp_callback`; штатный путь зависит от карт в кошельке | Приходит ли событие при погасшем экране; хватает ли времени на первый ответ; батарея | Исследование, не MVP |
| **NFC-сканер и журнал** | Браслет сам читает метки: обходы, чек-поинты, активы | В прошивке есть `m1_sector_read` и reader-ветки | Reader mode, хранение журнала, синхронизация | B2B-ниша, 3–6 недель |
| **BLE-ключ к ПК** | Браслет подтверждает присутствие для разблокировки компьютера | Свой GATT-сервис есть | Сопряжение/шифрование BLE, challenge-response, клиент на ПК | Высокий риск безопасности |

### 4.3. Внешние блокеры

| Сценарий | Почему не сейчас |
| --- | --- |
| **Mir Pay / банковская карта** | `bindService` к HCE-службе Mir Pay отклонён из-за `BIND_NFC_SERVICE` уровня signature; нужен поддерживаемый SDK/токенизация/сертификация. Локальный NDEF-ответчик этого не решает. |
| **Транспортная карта** | Закрытая схема: ключи, персонализация, сертификация оператора. Эмулировать «своими руками» нельзя. |
| **Защищённый пропуск с криптой** | Нужен апплет в eSE и эмитент; хранение ключей в AP-памяти — небезопасно и несертифицируемо. |
| **Ключ автомобиля / гостиницы** | OEM/эмитент, часто UWB/SE; публичного пути нет. |
| **Паспорт, водительские права, ID** | Юридическая сила и защита; экран/NDEF этого не заменяют. |
| **Mi Home / умный дом без телефона** | У браслета нет Wi-Fi; текущий мост идёт через Pixel. Для автономности нужен BLE-шлюз или партнёрский протокол, а не только экран. |
| **Полноценный фон и уведомления** | Сон, пробуждение и энергопотребление не проверены; RF-wake не реализован. |

## 5. Фаворит: «Автономный NFC-кошелёк»

### 5.1. Сценарий

1. Пользователь один раз синхронизирует с телефоном набор записей: визитка, Wi-Fi, медкарта,
   ссылка на оплату, произвольные NDEF.
2. На браслете открывает приложение «Кошелёк», выбирает запись и нажимает **NFC** (или
   приложение стартует сеанс само при открытии).
3. Подносит браслет к телефону/считывателю. Браслет сам отвечает на APDU.
4. Через 30–60 секунд или при выходе сеанс останавливается, маршрут восстанавливается.

Телефон в шагах 2–4 не участвует. Он нужен только для шага 1 и для изменения данных.

### 5.2. Что входит в MVP

- Локальный Type 4 NDEF-ответчик: SELECT AID `D2760000850101`, SELECT `E103`/`E104`,
  READ BINARY, корректные `9000`/`6A82`/`6B00`/`6282`.
- Кэш выбранной NDEF-записи в RAM (до 1024 байт + NLEN), чтобы не читать yaffs на каждый APDU.
- Локальный старт: `api_start()` больше не возвращает `-1`; сеанс не требует BLE.
- Экран: выбранная запись, статус «NFC активно», обратный отсчёт, кнопка «Стоп».
- Автостоп: выход со страницы, тайм-аут, ошибка, перезагрузка. Восстановление маршрута.
- Тесты: 20+ чтений двумя телефонами и независимым считывателем; проверка очистки после
  выхода, сна и перезагрузки; измерение расхода батареи.

### 5.3. Критерии приёмки

- Телефон не подключён по BLE, приложение на Pixel закрыто — чтение NDEF работает.
- Содержимое совпадает с выбранной записью; повторные чтения стабильны.
- После выхода/тайм-аута маршрут восстановлен, штатный кошелёк и другие NFC-приложения
  не задеты.
- Каталог и выбор переживают перезагрузку; модуль поднимается без телефона.
- Расход батареи на один сеанс и в простое измерен и зафиксирован.

## 6. Что поменять в архитектуре

| Область | Сейчас | Нужно |
| --- | --- | --- |
| Обработка APDU | Pixel отвечает через BLE | Локальный state machine в модуле |
| Данные NDEF | В `catalog.bin`, в памяти только метаданные и хеши | Индекс смещений или чтение записи при старте с кэшем в RAM |
| Старт NFC | Только явная команда Pixel, `api_start()` = `-1` | Локальный старт из UI, без `transport_ready()` и без блокировки при неудачном BLE |
| Таймеры | Один 10-мс цикл; сон/смена страниц не проверены | Гарантированная очистка при уходе со страницы и засыпании |
| Экран | 336×480, без удержания | Удержание на время сеанса/QR, максимальная яркость |
| Хранилище | Только NDEF-каталог | Схема v2 для QR/штрихкодов, TOTP-семян, текстов |
| Часы | `CLOCK_MONOTONIC` | `CLOCK_REALTIME` или калибровка для TOTP |
| Безопасность | Модель доступа к GATT не описана | Аутентификация синхронизации, PIN/шифрование для секретов |
| Размер | Каталог уже больше старого слота 31 272 байта, упакован в FACE | Бюджет на код и ресурсы, проверка упаковщика |
| Автозагрузка | Lua-таймер циферблата | Отдельный «кошельковый» циферблат или подтверждённый `boot_start` |

## 7. Риски и ограничения

**Технические.**

- Очистка NFC-маршрута при выходе, сне и сбое — главный риск. Ошибка оставляет браслет в
  состоянии, где штатный NFC может не работать; нужен диагностируемый `RECOVERY`.
- Питание: сеанс короткий, но удержание экрана и таймеры могут быть дороже, чем кажется.
  Расход не измерен.
- Экран: яркость, удержание, читаемость QR/штрихкода на изогнутом стекле.
- Прошивка: все адреса и fingerprints привязаны к `3.201.026`; обновление ломает сборку.
- Размер: ELF и контейнер FACE ограничены; новые функции требуют контроля.

**Безопасность.**

- NDEF публичен по определению: любой, кто приложит телефон, прочитает запись. Нельзя
  класть туда пароли, полные медицинские данные или платёжные секреты без согласия.
- Синхронизация по BLE: модель доступа и шифрование не подтверждены; для чувствительных
  данных нужна аутентификация и подтверждение на браслете.
- TOTP/секреты: без secure element и PIN это компромисс; нужно шифрование и трезвая
  оценка модели угроз.
- Потеря браслета: удалённого стирания нет; данные остаются на устройстве.

**Юридические и этические.**

- Клонирование чужих пропусков и UID — недопустимо; сценарии доступа допустимы только для
  собственных карт и с согласия владельца системы.
- Приём оплаты по QR — это не эквайринг и не Mir Pay; нужно соблюдать правила банка,
  лимиты и налоговые требования.
- Медицинские данные — добровольное раскрытие; нужен минимальный набор и понятное
  предупреждение.

**Продуктовые.**

- Установка идёт через сторонний циферблат/Notify, а не через магазин; поддержка одной
  модели и одной прошивки — высокая стоимость сопровождения.
- Если пользователь сменит циферблат, автозагрузка может перестать работать.
- NFC-кошелёк конкурирует не с Mir Pay, а с «достал телефон и показал»; выигрыш должен
  быть в скорости и отсутствии телефона.

## 8. Рекомендуемый план

| Этап | Срок | Результат |
| --- | --- | --- |
| 1. Локальный NDEF-ответчик | 1–2 недели | Чтение без BLE и без Pixel; аппаратный отчёт |
| 2. Шаблоны и UX | 1–2 недели | Визитка, Wi-Fi, медкарта, ссылка на оплату; экран и автостоп |
| 3. QR/штрихкод-кошелёк | 2–4 недели | Лояльность и статические билеты; проверка сканеров |
| 4. TOTP | 2–4 недели | PIN, шифрование, реальное время; решение по безопасности |
| 5. Исследования | параллельно, тайм-бокс | UID-домофон, eSE-партнёр, RF-wake |

**Решение о фокусе.** Если UID-домофон подтвердится на конкретном считывателе и окажется
легальным для собственного пропуска — это самый сильный бытовой сценарий. Если нет —
фокус на NDEF-кошельке, QR и TOTP; доступ и оплату двигать только через партнёров.

## 9. Что не обещать

- «Браслет заменит Mir Pay» — нет: нужен платёжный обработчик и токенизация.
- «Браслет заменит транспортную карту» — нет: нужен эмитент.
- «Любой домофон» — нет: UID-сценарий зависит от считывателя и не проверен.
- «Работает в фоне и от поля» — нет: RF-wake не реализован, батарея не измерена.
- «Все сканеры читают QR с браслета» — нет: нужен тест на конкретных моделях.
- «Данные защищены» — нет: NDEF публичен, secure element для наших секретов не подтверждён.
