# Tag Bridge — каталог и NFC-метки

Отдельная экспериментальная ветка для **Pixel 8a + Mi Smart Band 10 Pro Ceramic Global**, точная модель `miwear.watch.p67glt`, прошивка **3.201.026**. На Pixel хранится каталог, на браслете отображается выбранная запись. Поддерживаемое содержимое передаётся считывателю по NFC через Bluetooth-мост.

**Статус на 13 ноября 2026 года: один полный аппаратный прогон APK 0.3 + FACE v2 завершён успешно.** Созданная на Pixel текстовая запись `NFC-Test` (`Hello-from-Pixel`, NDEF — **23 байта**) прочитана с браслета по NFC за **6 APDU**. Содержимое совпало с каталогом; независимый BLE-журнал подтвердил каждую пару APDU и завершение ATT-записи ответа. После обмена получены `STOPPED` и повторный `QUERY → STOPPED`; финальная остановка и отключение также подтверждены. Пользователь подтвердил экран `NFC-Test / NDEF / SELECTED` после **REFRESH**. [Аппаратный отчёт](../docs/evidence/tags/pixel-0.3-v2-readback.json) · [Журнал](../docs/evidence/tags/pixel-0.3-v2-readback-log.txt).

Сохранены проверенные [APK 0.3](../releases/tags/tag-bridge-0.3.apk), [FACE v2](../releases/tags/tag-bridge-v2-p67glt-3.201.026.face), [ELF v2](../releases/tags/tag-bridge-v2-p67glt-3.201.026.elf), [manifest](../releases/tags/manifest.json) и [SHA256SUMS](../releases/tags/SHA256SUMS). Проходят **170 JVM-проверок и шесть нативных наборов с ASAN/UBSAN**. Файлы исходного APDU Lab v6 сохраняются без изменений; его синтетический тест и этот NDEF-прогон имеют отдельные отчёты.

Первая попытка readback завершилась `NFC transmit failed`; причина не установлена, очистка подтверждена. Успешный повтор доказывает полный путь для этой записи, но не длительную устойчивость. Приложение и циферблат оставались открытыми. Считывание настоящей физической метки, фоновая работа и работа после сна пока не проверены. Создание и сохранение записи проверены, включая сохранность каталога после обновления APK.

## Что поддерживается

| Действие | APK 0.3 / FACE v2 |
| --- | --- |
| Создать метку | Текст или ссылка в формате NDEF |
| Считать метку телефоном | Доступный UID, технология, ATQA/SAK/ISO-DEP; NDEF, если он читается стандартным Android API |
| Сохранить | До 32 записей; сообщение NDEF до 1024 байт; выбор, переименование и удаление |
| Показать на браслете | Одна выбранная на Pixel запись: имя, исходный UID как справочная информация, технология и состояние |
| Эмулировать NFC | **Содержимое NDEF как read-only NFC Type 4** через обработчик на Pixel |
| Пропуска, домофонные и транспортные карты | Сохранение доступного описания; без подходящего NDEF эмуляция недоступна |

Эмуляция NDEF не копирует UID, аппаратный тип исходной карты, защищённые сектора, ключи, баланс или права доступа. Pixel не считывает низкочастотные ключи на 125 кГц через NFC. В приложении неподдерживаемая запись остаётся видимой в каталоге, но кнопка NFC-эмуляции для неё выключена.

Полный каталог пока находится на телефоне; на браслете нет меню выбора всех записей. Имя на браслете передаётся в ASCII-транслитерации, а оригинальное имя на Pixel сохраняется. NFC требует подключённого Pixel, открытого приложения и активного циферблата.

Принят **ручной режим с активным экраном**: пользователь будит браслет перед использованием. Постоянная фоновая эмуляция и удержание браслета бодрствующим не планируются. Пробуждение по событию поля NFC описано как будущая опция в [ТЗ](../docs/technical-spec.md); её реализация отложена. Расход батареи ещё не измерен.

## Запуск

1. Собрать или взять соответствующие друг другу APK и FACE этой ветки. APK — отдельное приложение **«Метки · NFC»**, пакет `dev.mbapdu.tags`; оно не заменяет APDU Lab.
2. Передать `tag-bridge-v2-p67glt-3.201.026.face` из `releases/tags/` через режим разработчика Notify for Xiaomi, как описано в [основной инструкции](../README.md#запуск-теста).
3. Перезагрузить браслет при переходе между APDU Lab и Tag Bridge. Открыть циферблат **NFC Tags v2**, нажать **INSTALL TAGS** один раз. Модуль остаётся в памяти до перезагрузки; `rmmod` не используется.
4. На Pixel создать текст/ссылку либо нажать **«Считать метку телефоном»**. Выбрать сохранённую запись. Считывание не изменяет исходную карту.
5. Нажать **«Подключить сопряжённый браслет»**, выдать разрешения Bluetooth и выбрать браслет. При необходимости ввести его BLE-адрес. Приложение проверит отдельный GATT-сервис Tag Bridge.
6. Дождаться `QUERY → STOPPED` и передачи выбранной записи: `TAG_OK` вместе с подтверждением ATT-записи. Нажать **REFRESH** на браслете, чтобы обновить отображение.
7. Для записи с NDEF нажать **«Включить NFC-эмуляцию NDEF»**. Только `READY` с завершённой ATT-записью подтверждает запуск. После этого браслет можно поднести к другому телефону или считывателю.
8. Завершить кнопкой **«Остановить NFC и отключиться»**, дождавшись `STOPPED`. При ошибке очистки сохранить журнал и перезагрузить браслет; ошибка не равна успешной остановке.

После перезагрузки браслета модуль требуется загрузить снова. После переподключения BLE выбранная запись передаётся заново. Смена записи и редактирование каталога во время активного NFC-сеанса заблокированы. В v2 кнопка **DIAGNOSTICS** показывает `stage`, `rc`, `state`; она помогает отличить загрузку модуля от подключения телефона.

В 0.3 исправлено обнаружение сервиса после прежнего APDU Lab: при устаревшем GATT-кэше выполняется одна попытка обновления с сохранением соединения и последующим discovery. `refresh=true` означает только принятие запроса; готовность определяется обнаружением нового сервиса и ответами браслета. Этот путь с сервисом Tag Bridge проверен на Pixel.

## Проверка с одним Pixel

После READY нажать **«Проверить браслет этим Pixel»** и приложить браслет к NFC-антенне телефона. Здесь Pixel одновременно выполняет независимые роли NFC-считывателя и BLE-обработчика:

```text
Pixel IsoDep → NFC браслета → BLE → обработчик NDEF на Pixel
             ← NFC браслета ← BLE ← ответ
```

Считыватель выбирает NDEF-приложение, читает Capability Container, NLEN и содержимое. PASS требует совпадения полученных байтов с выбранной записью, каждой пары APDU с независимыми BLE-событиями и завершённых ATT-записей. После обмена отдельно подтверждаются STOPPED и повторный QUERY. На прикладывание и проверку отведено 30 секунд с нажатия кнопки; удерживать браслет неподвижно до результата. Именно этим способом выполнен сохранённый аппаратный прогон. Его доказательство — журнал приложения и независимое сопоставление NFC/BLE, а не сырая запись радиообмена.

## Сборка и устройство

Из корня проекта, в той же локальной среде JDK/Android SDK/NDK, что используется APDU Lab:

```sh
python3 tags/android/build.py
python3 tags/test_host.py
python3 tags/build_band.py
```

Результаты: `tags/android/build/tag-bridge-debug.apk`, `tags/build/tag-bridge-p67glt-3.201.026.elf` и `tags/build/tag-bridge-p67glt-3.201.026.face`. Эти временные сборки не заменяют сохранённые релизы.

Сборка браслета по умолчанию воспроизводит проверенную v2. Необязательный `python3 tags/build_band.py --diagnostic-v3` создаёт отдельный диагностический кандидат: `tags/build/tag-bridge-v3-p67glt-3.201.026.face` и соответствующий ELF. Эта версия на устройстве не проверена и не входит в сохранённый релиз.

Android использует отдельный package и отдельные GATT UUID. Нативная сборка включает `TRANSPORT_TAG_PROFILE`, меняющий AID на `D2760000850101`; стандартный профиль APDU Lab остаётся отдельным. В исходном контейнере FACE сохраняются размеры ресурсов, проверяются модель/прошивка, ABI, constructor и релокации. Для размещения нового модуля удаляются ненужные символы ELF с проверкой сохранности загружаемых байтов и смысла релокаций.

Пределы: CAPDU ≤261, RAPDU ≤258 байт; первое SELECT-приложения — в одном NCI-пакете; ожидание ответа APDU — 3 секунды; NFC-сеанс — 120 секунд. Нативный модуль допускает только SELECT и READ BINARY этой NDEF-ветки; запись файлов не реализована. Работа после сна и в фоне ещё требует аппаратной проверки.

Подробности Pixel и wire-протокола: [Android README](android/README.md). Архитектура исходного NFC-моста и ограничения маршрутизации: [основная архитектура](../docs/architecture.md).

Для входа через Roundabout подготовлены отдельная native-страница и копия **Roundabout RU NFC** с нижним кругом «Метки». Общий `jump_app` с таблицей 39 строк и обработчик круглого Widget — разные пути. Во втором подтверждена передача native app ID; новая копия использует собственный `0xD4`, сохраняя две верхние кнопки. Открытие страницы, синхронизация и отображение `NFC-Test` проверены на браслете. Установленный UI v1 требует исправления наложений; по последнему запросу сначала показывается компактный макет без прокрутки. Будущий каталог с кнопками переключения описан в ТЗ и пока не реализован. [Интеграция](../docs/roundabout-nfc.md) · [Разбор прошивки](ui-research/README.md).

Виджет, открываемый свайпом слева, использует другой реестр. Метод `widgets_add` найден, но структура его аргументов и жизненный цикл ещё не восстановлены. Текущий запуск выполняется через отдельный циферблат, а не через системный виджет.

Добавление этих NDEF-записей в стандартный **Xiaomi Pay** не реализовано. [Официальный FAQ Xiaomi для этой серии](https://www.mi.com/uk/support/faq/details/KA-703616/) не заявляет поддержку добавления и эмуляции пропусков на момент проверки. В образе есть ресурсы `access_card` и операция `SYNC_CARD_LIST`, но они не подтверждают доступный импорт произвольных меток. Этот путь остаётся отдельным исследованием; штатный кошелёк не изменяется.
